# AI 서버 의견·할 일 형식 (AI-05) v0.1 초안

> 안건별 의견·근거와 할 일(AI-05)을 안건 보드(연동 API 초안 3.2)에 담아 보내는 방식, 사람이 고친 의견·할 일과 참석자 명단을 받는 방식을 다룬다. 아직 cn 팀과 확인하기 전의 AI 쪽 제안이다. 확정되면 이 문서를 최신 전체본 하나로 교체한다.
> 안건 목록과 줄별 분류는 `agenda-contract.md`, 안건 보드 전체 모양과 요약은 `agenda-summary-contract.md`, 안건 상태는 `agenda-status-contract.md`에 있다.

- 근거: PRD v0.1 AI-05, 요구사항 REQ-077, 연동 API 초안 3.2 (`opinions`)와 4장 (`todos`)
- 예시 파일: `examples/api/` (아래 14장)

## 1. 목적과 범위

| 구분 | 내용 |
|---|---|
| 목적 | 의견이 갈릴 때 어디서 갈리는지 보여 주고, 회의 중 나온 할 일을 바로 보여 준다. 회의 후 다르게 이해하는 일을 줄인다 |
| 다루는 것 | 안건 보드의 `opinions` 채우기, 안건 보드의 새 칸 `todos` 채우기, 사람이 고친 의견·할 일 받기, 참석자 명단 받기 |
| 의견과 할 일의 관계 | 모델 호출을 따로 한다. 입력, 검증 규칙, 갱신 시작 조건이 다르고, 한쪽이 멈춰도 다른 쪽은 계속 동작해야 하기 때문이다 |
| 이 문서 밖 | 주제 변경 감지(AI-06), 미결 안건 추출(AI-07), 오늘 회의 요약(AI-08) |

AI-08은 새로 정리하지 않고 이 결과를 모아 배치한다. 그래서 근거 연결 정보(`evidenceSeqs`)와 사람이 고친 표시(`edited`, `needsCheck`)가 AI-08까지 그대로 이어진다.

## 2. 흐름

| 번호 | 내용 | 보내는 쪽 | 받는 쪽 | 방식 | 보내는 때 |
|---|---|---|---|---|---|
| 1 | 안건 보드 (의견·할 일 포함) | ai-service | 백엔드 | `PUT {백엔드 주소}/internal/meetings/{meetingId}/agenda-board` | 담을 값이 바뀔 때, 최대 초당 1번 |
| 2 | 사람이 고친 의견·할 일 | 백엔드 | ai-service | `POST /internal/meetings/{meetingId}/agenda-item-edits` | 안건 보드에서 고칠 때 바로 |
| 3 | 참석자 명단 | 백엔드 | ai-service | 기존 안건 목록 요청 `PUT /internal/meetings/{meetingId}/agendas`에 `attendees` 추가 | 안건 목록을 보낼 때 함께 |

- 1번은 `agenda-summary-contract.md` 4장과 같은 주소, 같은 재시도 규칙, 같은 `version` 규칙을 쓴다.
- 2번은 받으면 바로 응답하고, 반영은 뒤에서 한다.
- 3번은 새 주소를 만들지 않는다. 재시작 복구 때 백엔드가 안건 목록을 먼저 다시 보내는 흐름(`agenda-contract.md` 9장)에 그대로 실린다.

## 3. 공통 규칙

| 규칙 | 내용 |
|---|---|
| 필드 이름 | camelCase |
| `meetingId`, `agendaId` | 받은 타입 그대로 돌려준다 (`agenda-contract.md` 3장) |
| 근거 | `evidenceSeqs`는 근거가 된 전사 줄의 `seq`이다. 요약 문장(`agenda-summary-contract.md` 3장)과 같은 방식이다 |
| `seq` | `input-contract.md`의 `lines[].seq`와 같다. 식별용 번호이고 시간 순서가 아니다 |
| 항목 번호 `id` | 뜻이 없는 문자열이며 회의 안에서 겹치지 않는다. 재시작 뒤에도 겹치지 않게 만든다. 사람이 고친 항목만 갱신해도 같은 번호를 유지하고, AI가 만든 항목의 번호는 갱신할 때 바뀔 수 있다 |

## 4. 안건 보드 보내기 (ai-service → 백엔드)

본문의 모양(`version`, `basedOnSeq`, `currentAgendaId`, `agendas`, `offTopic`)과 `status`, `statusReason`, `summary`는 `agenda-summary-contract.md` 4장, `agenda-status-contract.md` 3장과 같다. 이 문서는 `agendas[]`의 `opinions`와 새 칸 `todos`만 정한다.

```json
{
  "agendaId": 101,
  "status": "DISCUSSING",
  "statusReason": {"text": "...", "evidenceSeqs": [45]},
  "summary": [],
  "opinions": [],
  "todos": []
}
```

- 모든 안건은 항상 `opinions`와 `todos`를 가진다. 담을 항목이 없으면 빈 배열이다.
- `todos`는 연동 API 초안 3.2에 없는 새 칸이다. PRD가 "안건별 할 일"이라고 해서 안건 안에 둔다. 초안 4장(오늘 회의 요약)의 `todos`와 같은 이름·비슷한 모양으로 맞춰 AI-08이 가져가기 쉽게 한다.

### 4.1 opinions의 항목

| 필드 | 타입 | 설명 |
|---|---|---|
| `id` | 문자열 | 항목 번호. 3장 규칙 |
| `text` | 문자열 | 의견 한 줄. 발언자가 아니라 내용 기준이다 |
| `kind` | 문자열 | `OPINION`(의견), `EVIDENCE`(근거), `CONCERN`(우려), `QUESTION`(질문). 초안 3.2의 값을 그대로 쓴다 |
| `evidenceSeqs` | 정수 배열 | 근거가 된 전사 줄 번호. 1개 이상 |
| `edited` | 불리언 | 사람이 고친 항목이면 `true`. 고친 항목은 갱신해도 바꾸지 않는다 (5장) |
| `needsCheck` | 불리언 | "확인 필요" 표시. 고친 항목의 근거가 달라졌을 때 `true` (10장) |

- 근거 발언 줄(`evidenceSeqs`)이 없는 항목은 만들지도 보내지도 않는다.
- `EVIDENCE`는 어떤 의견의 이유로 발언에 나온 말이다. 이유가 발언에 없는 의견에는 `EVIDENCE` 항목을 만들지 않는다. AI가 근거를 만들어 넣지 않는다 (PRD AI-05).
- 순서는 모델이 낸 순서이다. 같은 안에 대한 의견·근거·우려를 이어서 나열하게 한다. 사람이 고친 항목은 맨 앞에 둔다 (제안).

### 4.2 todos의 항목

| 필드 | 타입 | 설명 |
|---|---|---|
| `id` | 문자열 | 항목 번호. 3장 규칙 |
| `task` | 문자열 | 할 일 한 줄 |
| `assigneeName` | 문자열 또는 null | 발언에 나온 이름 그대로. 이름이 없으면 `null` |
| `assigneeStatus` | 문자열 또는 null | 참석자 명단과 맞춘 결과. 아래 표 |
| `assigneeUserId` | 문자열·정수 또는 null | `assigneeStatus`가 `MATCHED`일 때만 명단의 `userId`를 돌려준다. 아니면 `null` |
| `dueText` | 문자열 또는 null | 기한을 말한 그대로("수요일까지"). 없으면 `null`이고 화면에는 "기한 미정"으로 보여 준다. 날짜로 바꾸지 않는다 |
| `evidenceSeqs` | 정수 배열 | 근거가 된 전사 줄 번호. 1개 이상 |
| `edited` | 불리언 | 사람이 고친 항목이면 `true` |
| `needsCheck` | 불리언 | 고친 항목의 근거가 달라졌을 때 `true`. 의견과 같은 뜻 |
| `unclear` | 불리언 | 할 일인지 분명하지 않은 발언이면 `true`. 화면에는 "할 일 확인 필요"로 보여 준다 |

`assigneeStatus` 값:

| 값 | 화면 표현 | 뜻 |
|---|---|---|
| `MATCHED` | (이름 표시) | 명단의 한 사람과 맞았다 |
| `UNASSIGNED` | 담당자 미정 | 발언에 이름이 없다 |
| `NOT_IN_ROSTER` | 명단에 없는 담당자 | 이름이 있으나 명단의 누구와도 맞지 않는다. 참석자가 확인한다 |
| `AMBIGUOUS` | 담당자 확인 필요 | 명단에서 맞는 사람이 둘 이상이다 (동명이인). 이름은 AI 제안 |
| `null` | (이름 표시) | 이름은 있으나 명단을 받지 못해 비교하지 못했다 |

- `needsCheck`(고친 항목의 근거가 달라짐)와 `unclear`(할 일인지 불분명)는 뜻이 달라서 칸을 따로 둔다.
- 화자를 구분하지 않으므로 "제가 할게요"처럼 이름이 없는 발언은 담당자를 알 수 없고 `UNASSIGNED`가 된다.
- 순서는 근거 줄의 시작 시각 순이다. 사람이 고친 항목은 맨 앞에 둔다 (제안).

### 4.3 보내는 때와 응답

- 담을 값이 마지막으로 보낸 것과 달라졌을 때 보낸다. 같으면 보내지 않는다. 최대 초당 1번이다.
- 회의 `end` 알림을 처리하면서 바뀐 것이 있으면 마지막 상태를 보낸다. 백엔드는 가장 큰 `version`을 최종으로 본다.
- `version` 규칙, 응답, 재시도는 `agenda-summary-contract.md` 4.5·4.6과 같다.

## 5. 사람이 고친 의견·할 일 받기 (백엔드 → ai-service)

사용자가 안건 보드에서 의견이나 할 일을 고치거나, "확인 필요" 표시를 확인했다고 표시하면 백엔드가 바로 알린다. 한 요청에 의견과 할 일을 함께 담을 수 있다.

### 5.1 본문

| 필드 | 타입 | 설명 |
|---|---|---|
| `meetingId` | 문자열 또는 정수 | 주소의 값과 같아야 한다 |
| `edits` | 배열 | 고친 항목. 한 번에 여러 개를 보낼 수 있다 |

### 5.2 edits의 항목

| 필드 | 타입 | 의견 `edit` | 할 일 `edit` | `confirm` | 설명 |
|---|---|---|---|---|---|
| `agendaId` | 안건 번호 | 필수 | 필수 | 필수 | 항목이 속한 안건 |
| `target` | 문자열 | 필수 | 필수 | 필수 | `"opinion"` 또는 `"todo"` |
| `itemId` | 문자열 | 필수 | 필수 | 필수 | 4장의 항목 번호 |
| `action` | 문자열 | 필수 | 필수 | 필수 | `"edit"`(고침) 또는 `"confirm"`(확인 필요를 확인함) |
| `rev` | 정수 | 필수 | 필수 | 필수 | 그 항목을 고치거나 확인한 횟수. 올라갈 때마다 커지면 되고 시작값은 상관없다. 같은 `itemId`는 `rev`가 큰 것만 반영한다 |
| `text` | 문자열 | 필수 | 없음 | 없음 | 고친 의견. 비어 있으면 안 된다 |
| `kind` | 문자열 | 필수 | 없음 | 없음 | 4.1의 값 |
| `task` | 문자열 | 없음 | 필수 | 없음 | 고친 할 일. 비어 있으면 안 된다 |
| `assigneeName` | 문자열 또는 null | 없음 | 선택 | 없음 | 고친 담당자 이름. 없으면 `null` |
| `assigneeUserId` | 문자열·정수 또는 null | 없음 | 선택 | 없음 | 사용자가 명단에서 직접 고른 경우의 `userId` |
| `dueText` | 문자열 또는 null | 없음 | 선택 | 없음 | 고친 기한. 없으면 `null` |
| `evidenceSeqs` | 정수 배열 | 필수 | 필수 | 없음 | 그 항목의 근거 줄 번호. 비어 있지 않아야 한다. 백엔드가 저장한 값을 그대로 보낸다 |

`edit`에 항목 내용을 모두 함께 보내게 한 이유는 11장의 복구 때문이다. ai-service는 재시작하면 항목을 모두 잃으므로, 백엔드가 고친 항목을 다시 보낼 때 항목이 자기 안에 필요한 정보를 모두 갖고 있어야 한다.

### 5.3 ai-service의 처리

| 번호 | 규칙 |
|---|---|
| 1 | `edit`을 받으면 그 항목을 고정한다. 내용을 보낸 값으로 바꾸고 `edited`를 `true`로 한다. 이후 갱신에서 다시 만들거나 덮어쓰지 않는다 |
| 2 | 고친 항목은 사람이 쓴 글이므로 근거 검증기를 거치지 않는다 |
| 3 | 고친 할 일의 `assigneeStatus`는 보낸 `assigneeName`을 명단과 다시 맞춰서 정한다 (6.3). `assigneeUserId`가 명단에 있으면 그 사람으로 `MATCHED`가 된다. 고친 할 일은 `unclear`가 `false`이다 |
| 4 | `itemId`를 모르는 `edit`은 새 고정 항목으로 만들어 그 안건에 넣는다. 재시작 뒤 복구(11장)이거나, 사용자가 고치는 사이에 AI가 그 항목을 새로 만든 항목으로 바꾼 경우이다. 뒤의 경우에는 비슷한 항목이 둘 생길 수 있다 |
| 5 | `confirm`을 받으면 그 항목의 `needsCheck`를 `false`로 한다. 항목은 고정된 채로 남는다. 고치지 않은 항목에 대한 `confirm`은 무시한다 |
| 6 | 고쳤거나 확인한 안건은 다음 주기에 바로 다시 만든다 (9장). 고친 항목은 같은 안건의 다른 항목을 만들 때 "이미 있는 항목"으로만 쓴다 |
| 7 | 안건 목록에 없는 `agendaId`도 받아서 보관한다. 안건 목록이 늦게 도착한 경우일 수 있어서다. 목록에서 사라진 안건이면 10장대로 버린다 |
| 8 | `rev`가 같거나 작아서 반영하지 않은 항목은 응답의 `ignored`에 담는다 |

### 5.4 응답

| 상황 | 응답 |
|---|---|
| 받음 | `200` + `{"accepted": true, "result": "accepted", "applied": 2, "ignored": []}`. `applied`는 새로 반영한 항목 수 |
| 모두 이미 반영된 `rev`이거나 무시된 항목 | `200` + `{"accepted": true, "result": "stale", "applied": 0, "ignored": [{"itemId": "...", "reason": "stale"}]}` |
| 형식 오류, 주소와 본문의 `meetingId` 불일치, `target`이 `opinion`·`todo`가 아님, `edit`에 필수 칸이 없음 | `400` + `{"error": "INVALID_INPUT", "detail": "이유"}` |
| 아직 받을 수 없음 | `503` + `{"error": "NOT_READY", "detail": "이유"}` |

`ignored`의 `reason`은 `"stale"`(`rev`가 오래됨), `"not_edited"`(고치지 않은 항목에 대한 `confirm`)이다.

## 6. 참석자 명단 받기 (백엔드 → ai-service)

할 일의 담당자를 명단과 맞추려면 명단이 필요하다. 현재 ai-service로 오는 요청에는 명단이 없다 (노션 연동 API 초안의 `attendees`는 회의록 초안 요청에만 있다). 안건 목록 요청(`agenda-contract.md` 4장)의 본문에 선택 필드를 하나 추가한다.

### 6.1 추가 필드

| 필드 | 타입 | 설명 |
|---|---|---|
| `attendees` | 배열 | 참석자 명단. 항목은 `userId`(문자열 또는 정수)와 `name`(문자열, 비어 있으면 안 됨). 선택 |

```json
"attendees": [
  {"userId": 7, "name": "김철수"},
  {"userId": 8, "name": "이영희"}
]
```

### 6.2 규칙

| 번호 | 규칙 |
|---|---|
| 1 | `attendees`가 있으면 받은 명단으로 통째로 바꾼다. 필드가 없으면 이전에 받은 명단을 그대로 둔다 |
| 2 | 명단은 안건 목록과 같은 `version`으로 거른다. `version`이 같거나 작으면 안건 목록과 함께 명단도 무시하므로, 백엔드는 명단이 바뀔 때도 `version`을 올려야 한다 |
| 3 | 명단이 비어 있거나 한 번도 받지 못했으면 이름을 맞추지 않는다. 이름이 있는 할 일의 `assigneeStatus`는 `null`이다. 모든 이름이 "명단에 없는 담당자"로 보이는 것을 막으려는 것이다 |
| 4 | 명단이 바뀌면 이미 만든 할 일의 `assigneeStatus`와 `assigneeUserId`를 모델 호출 없이 다시 맞춘다 |
| 5 | 회의 정보는 시작 전에만 고칠 수 있다고 cn 팀이 답했다. 그래서 명단은 대개 회의 시작 전에 한 번 온다. 회의 중에 바뀌는 경우도 받는다 |

### 6.3 이름 맞추기

이름 맞추기는 모델이 아니라 코드가 한다. 모델에는 명단을 보여 주지 않고, 발언에 나온 이름만 뽑게 한다. 모델이 명단을 보고 이름을 지어내는 것을 막고, 규칙을 시험할 수 있게 하려는 것이다.

| 순서 | 규칙 |
|---|---|
| 1 | 비교 전에 이름 끝의 호칭("님", "씨")을 떼고, 공백과 영문 대소문자 차이는 무시한다 |
| 2 | 명단 이름과 정확히 같은 사람이 1명이면 `MATCHED` |
| 3 | 정확히 같은 사람이 없으면, 명단 이름의 첫 글자를 성으로 보고 뗀 이름이 같은 사람을 찾는다. 1명이면 `MATCHED` (예: "철수" → "김철수") |
| 4 | 2 또는 3에서 맞는 사람이 2명 이상이면 `AMBIGUOUS` |
| 5 | 아무도 맞지 않으면 `NOT_IN_ROSTER` |

두 글자 성처럼 첫 글자만 성이 아닌 이름은 3번에서 맞지 않아 `NOT_IN_ROSTER`가 될 수 있다. 이번 범위에서는 다루지 않는다 (12장).

## 7. ai-service의 의견 규칙

| 번호 | 규칙 |
|---|---|
| 1 | 입력은 분류 결과가 그 안건인 전사 줄이다. 맞장구는 바로 앞에 분류된 줄의 안건에 붙인다 (앞 줄 끝에서 10초 이내, 그 사이에 해당 없음 줄이 없을 때). 간투사, 낮은 확신도 줄, 해당 없음 줄, 안건 요약 문장은 넣지 않는다. 사람이 고쳐서 고정된 분류는 그대로 믿고 쓴다 |
| 2 | 안건 제목과 결정할 사항을 함께 보여 주되, 줄에 없는 내용을 제목에서 가져와 쓰지 않는다 |
| 3 | 발언자가 아니라 내용 기준으로 정리한다. 같은 의견이 반복되면 하나로 합친다. 같은 안에 대한 의견·근거·우려는 이어서 나열한다 |
| 4 | `EVIDENCE`는 발언에 나온 이유만 쓴다. 이유가 없는 의견에는 만들지 않는다 |
| 5 | 모든 항목은 근거 줄이 있어야 한다. 인용, 숫자, STT 불확실 표시를 검증기(`agenda-summary-contract.md` 6장과 같은 것)로 확인하고, 통과하지 못하면 오류를 알려 1회 더 부른다. 그래도 통과하지 못한 항목은 보내지 않는다. 이때는 연속 실패로 세지 않는다 |
| 6 | 갱신할 때마다 그 안건의 원문 줄에서 새로 만든다. 앞서 만든 항목 위에 쌓지 않는다 |
| 7 | 사람이 고친 항목은 갱신하지 않는다 (5.3의 1번). 모델에는 고친 항목을 "이미 있는 항목"으로 보여 주어 같은 내용을 다시 만들지 않게 한다 |
| 8 | 안건당 항목 수의 상한을 둔다 (제안, 값은 구현 때 정하고 평가 뒤 조정). 사람이 고친 항목이 먼저 자리를 차지한다 |
| 9 | 로그와 상태 조회에 전사 내용, 안건 제목, 의견 문장을 남기지 않는다. 회의 번호, 개수, 예외 이름만 남긴다 |

## 8. ai-service의 할 일 규칙

| 번호 | 규칙 |
|---|---|
| 1 | 입력은 7장 1번과 같다. 참석자 명단은 모델에 주지 않는다 |
| 2 | 누가 무엇을 하겠다, 하자, 해 달라고 한 발언에서만 할 일을 뽑는다. 단순한 의견과 질문은 할 일이 아니다 |
| 3 | 담당자는 발언에 나온 이름을 그대로 뽑는다. 이름이 없으면 `null`이다. 명단이나 문맥으로 이름을 추측하지 않는다 |
| 4 | 이름과 명단 맞추기는 코드가 한다 (6.3) |
| 5 | 기한은 말한 그대로 `dueText`에 담는다. 날짜로 바꾸지 않는다. 없으면 `null` |
| 6 | 모든 항목은 근거 줄이 있어야 하고, 할 일 문장은 7장 5번의 검증기를 거친다 |
| 7 | `assigneeName`과 `dueText`는 근거 줄의 글에 그대로 있어야 한다 (제안). 없으면 그 값을 `null`로 바꾸고 `unclear`를 켠다. 모델이 지어낸 값을 막으려는 것이다 |
| 8 | 할 일인지 분명하지 않은 발언(예: 누가 좀 알아보자는 말)은 `unclear`를 켠 항목으로 만든다 |
| 9 | 같은 담당자의 같은 일이 반복되면 하나로 합친다 |
| 10 | 갱신할 때마다 원문 줄에서 새로 만들고, 고친 항목은 7장 6·7번과 같이 다룬다 |
| 11 | 한 번 뽑은 할 일이 이후 발언에서 취소되거나 바뀌는 것은 이번 단계에서 감지하지 않는다 (12장) |
| 12 | 로그와 상태 조회에 전사 내용, 이름, 할 일 문장을 남기지 않는다 |

## 9. 갱신 시점

값은 모두 제안이며 평가 뒤에 조정한다.

| 번호 | 규칙 |
|---|---|
| 1 | 분류 → 상태 판정 → 안건 요약 단계 뒤에 같은 처리 흐름에서 의견 → 할 일 단계를 이어서 돈다. 단계들이 서로 다른 시점의 분류를 보지 않게 하려는 것이다 |
| 2 | 새 줄이 붙은 안건만 다시 만든다 |
| 3 | 의견은 그 안건에 연결된 줄이 4줄 이상일 때부터 호출한다. 줄이 적으면 갈릴 의견이 없어 빈 호출이 되기 때문이다 |
| 4 | 할 일은 줄 수 조건 없이 호출한다. 한 줄로도 할 일이 생기기 때문이다. 호출 전에 신호 단어를 검사해 거르지 않는다. 규칙이 놓치면 할 일이 빠지기 때문이다 |
| 5 | 의견과 할 일 모두 새 줄이 4개 이상이면 바로, 1~3개이면 최대 60초(음성 시간)까지 기다렸다가 호출한다. 4는 비용을 줄이려고 평가(회의 A·B)에서 쓴 값이다 |
| 6 | 분류가 바뀌어 줄을 잃거나 얻은 안건, 사람이 분류를 고친 줄이 속한 안건, 사람이 항목을 고치거나 확인한 안건은 5번의 기다림 없이 다음 주기에 호출한다 |
| 7 | 참석자 명단이 바뀌면 할 일의 이름 맞추기만 다시 한다 (6.2의 4번). 모델은 부르지 않는다 |
| 8 | 회의 `end` 알림을 처리한 뒤 모든 안건을 마지막으로 한 번 처리하고, 바뀐 것이 있으면 보낸다 |
| 9 | 의견과 할 일은 각각 따로 센다. 연속 3번 실패하면 그 기능만 멈추고, 회의당 호출 상한(각 300)에 닿아도 그 기능만 멈춘다. 한쪽이 멈춰도 다른 쪽과 분류·상태·요약·보드 전송은 계속된다. 이미 낸 결과와 사람이 고친 항목은 계속 보낸다 |

| 환경변수 | 설명 | 기본값 |
|---|---|---|
| `AGENDA_OPINION_REFRESH_SEC` | 새 줄이 1개뿐일 때 의견 호출을 기다리는 시간(음성 시간 초) | 60 |
| `AGENDA_OPINION_MIN_LINES` | 의견 호출을 시작하는 최소 줄 수 | 4 |
| `MAX_AGENDA_OPINION_CALLS_PER_MEETING` | 회의당 의견 호출 상한 | 300 |
| `AGENDA_TODO_REFRESH_SEC` | 새 줄이 1개뿐일 때 할 일 호출을 기다리는 시간(음성 시간 초) | 60 |
| `MAX_AGENDA_TODO_CALLS_PER_MEETING` | 회의당 할 일 호출 상한 | 300 |

모델은 요약과 같은 `LLM_PROVIDER`, `LLM_MODEL`을 쓴다. `LLM_PROVIDER=echo`이면 모델을 부르지 않는다. 토큰·호출 시간 지표는 `ai.task=agenda_opinions`, `ai.task=agenda_todos`로 남는다.

## 10. 분류가 나중에 바뀔 때

분류는 새 줄이 올 때뿐 아니라 안건 변경·삭제나 사람의 수정으로도 바뀐다 (`agenda-contract.md` 8장).

| 상황 | 의견·할 일의 처리 |
|---|---|
| 줄이 안건 A에서 안건 B로 옮겨 감 | 최신 분류 기준으로 A와 B를 각각 원문 줄에서 다시 만든다. 이미 만든 항목을 고쳐 쓰지 않는다 |
| 고친 항목의 근거 줄이 다른 안건으로 옮겨 가거나 근거 줄의 글이 바뀌거나 줄이 사라짐 | 항목은 그대로 두고 `needsCheck`를 켠다. `confirm`을 받거나 사용자가 다시 고치면 끈다 |
| 안건이 삭제됨 | 그 안건의 의견·할 일을 지운다. 고친 항목도 함께 지운다. 안건 보드는 전체 상태이므로 목록에서 빠진 안건은 다음 상태에 담기지 않는다 |
| 안건의 제목·결정할 사항이 바뀜 | 이미 만든 항목은 다시 만들지 않는다. 다음에 그 안건이 갱신될 때부터 새 제목을 기준으로 한다 |

## 11. 복구

ai-service는 회의 상태를 메모리에만 둔다. 재시작하면 안건 목록, 참석자 명단, 분류, 의견·할 일이 모두 사라진다.

| 순서 | 내용 |
|---|---|
| 1 | 재시작 직후 모르는 회의의 줄 묶음이 오면 `409` + `{"expectedBatch": 1}`로 답한다 (`input-contract.md` 8장) |
| 2 | 백엔드는 줄 묶음을 1번부터 다시 보내기 전에 최신 안건 목록(**참석자 명단 포함**), 고친 분류 전체, 고친 요약 문장 전체에 더해 **사람이 고친 의견·할 일 전체**를 `agenda-item-edits`로 다시 보낸다. 항목마다 `action`은 `"edit"`, `rev`는 마지막 값이고 내용은 백엔드가 저장한 값이다 |
| 3 | ai-service는 안건 목록과 명단을 받은 뒤 고친 항목을 되살리고, 다시 받은 줄을 분류한 뒤 의견·할 일을 만든다. 고친 항목은 고정되어 있으므로 사람의 수정은 유지된다 |

- 고치지 않은 항목은 다시 보내지 않는다. 줄을 다시 받으면 AI가 새로 만든다.
- 되살린 항목의 근거 줄이 다시 분류된 결과와 어긋나면 10장에 따라 `needsCheck`가 켜진다.

## 12. 이번 범위에서 하지 않는 것

PRD에 없거나 결정할 수 있는 규칙이 없어 제안만 하고 구현하지 않는다.

| 항목 | 이유 |
|---|---|
| 의견·할 일의 삭제, 직접 추가, 잠금 해제 | PRD AI-05는 "수정"만 정한다. 필요하면 기획 확인 뒤 `action`을 늘린다 |
| 할 일의 기한을 날짜로 바꾸기 (`dueDate`) | 상대 표현("금요일까지")을 날짜로 바꾸면 틀리기 쉽고, 틀린 날짜가 말한 그대로 보여 주는 것보다 위험하다. 회의 날짜 기준 계산이 필요해지면 그때 정한다 |
| 이후 발언에서 할 일이 취소되거나 바뀌는 것 감지 | 결정할 수 있는 규칙이 없다 |
| "A안: 장점·우려"처럼 묶는 칸 | 칸이 늘면 검증·잠금·고침 처리가 복잡해진다. 평가에서 읽기 어려우면 추가한다 |
| 두 글자 성 등 이름 맞추기의 예외 | 6.3의 규칙만 쓴다 |
| 고친 뒤 쌓인 발언의 의미가 달라진 것을 감지 | 이번에는 근거가 달라진 경우만 감지한다 (10장) |
| `offTopic` 채우기 | AI-06. 그때까지 `null`로 보낸다 |

|---|---|

| 기한을 날짜 변환 없이 말한 그대로(`dueText`) 보여 준다 | AI 제안, cn 팀 확인 필요 (화면에서 괜찮은지) |
| 안건 목록 요청에 참석자 명단 `attendees`를 선택 필드로 추가한다 | AI 제안, cn 팀 확인 필요 |

| `edit` 요청에 항목 내용과 근거(`evidenceSeqs`)를 함께 담는다 | AI 제안, cn 팀 확인 필요 |
| 재시작 복구 때 고친 의견·할 일 전체와 참석자 명단을 먼저 다시 보낸다 | AI 제안, cn 팀 확인 필요 |
| 의견·할 일의 삭제·직접 추가 | 기획 확인 필요 (범위) |
| 의견은 안건 줄 4줄 이상부터, 갱신 조건(새 줄 4개 또는 60초), 호출 상한 각 300 | 제안값, 평가 뒤 조정 |
| 안건당 항목 수 상한 | 제안, 값은 구현 때 정함 |
| 지표 `ai.task` 값 `agenda_opinions`, `agenda_todos` | cn 팀 확인 필요 |

### 13.1 안건 보드(연동 API 초안 3.2)와의 관계

| 내용 | 가는 곳 | 구현 시점 |
|---|---|---|
| 안건별 요약 | 보드 `agendas[].summary` | AI-03 |
| 안건 상태와 판정 근거 | 보드 `agendas[].status`, `statusReason` | AI-04 |
| 의견·근거·우려·질문 | 보드 `agendas[].opinions` | AI-05 |
| 할 일 (담당자, 기한) | 보드 `agendas[].todos` (새 칸) | AI-05 |
| 주제 변경 | 보드 `offTopic` | AI-06 |

연동 API 초안 3.2와 다른 점은 `summary`의 형식(AI-03)과 이 문서의 `opinions` 항목 칸, 새 칸 `todos`이다. 나머지 칸은 초안을 그대로 쓴다.
