# AI 서버 안건 상태 판정 형식 (AI-04) v0.2 초안

> 안건 상태 판정(AI-04)을 **결정할 사항 단위**로 바꾼다. 안건 안의 결정할 사항마다 상태, 결정 내용 한 줄, 근거 발언을 만들고, 안건 상태는 그 결과에서 규칙으로 정한다. 안건 보드(연동 API 초안 3.2)에 담아 보내는 방식과, 사람이 고친 결정 내용을 받는 방식을 다룬다. 아직 cn 팀과 확인하기 전의 AI 쪽 제안이다. 칸 모양과 상태 값은 cn 팀이 요청한 것을 따랐다. 확정되면 이 문서를 최신 전체본 하나로 교체한다.
> 안건 목록과 줄별 분류는 `agenda-contract.md`, 안건별 요약과 보드 전체 모양은 `agenda-summary-contract.md`에 있다.

- 근거: PRD v0.1 AI-04, 요구사항 REQ-076·078·086·124·125·126, 연동 API 초안 3.2 (안건 보드 결과), cn 팀 답변(안건 보드 요청서 답변의 백엔드 요청 1~3), 2026-10-27 전체회의 답(기획팀·cn 팀)
- 설계: `ai04-decision-points-redesign-v2.md` (프로젝트 문서)
- 예시 파일: `examples/api/agenda-board-decision-points-put.json`, `examples/api/decision-edits-post.json`
- 평가: 평가 도구와 기준은 `summary/eval_agenda_status.py`, 결과는 평가 뒤 `docs/eval/`에 둔다 (결정할 사항 단위 평가는 새 합성 대본으로 하며 구현 뒤에 정한다)
- v0.1에서 바뀐 것: (1) 상태 판정이 안건 하나에 하나에서 결정할 사항마다 하나로 바뀌었다. (2) 안건 상태는 모델이 아니라 사항 상태에서 규칙으로 정한다. (3) 사항마다 결정 내용 문장(`decisionText`)과 근거를 만든다. 근거는 개수 상한이 없고 비어 있을 수 있다. (4) 사람이 고친 결정 내용을 받는 요청(`decision-edits`)이 새로 생겼다. (5) 안건의 `statusReason`은 모델이 쓴 문장이 아니라 코드가 만든 문장이 된다

## 1. 목적과 범위

| 구분 | 내용 |
|---|---|
| 목적 | 안건 안의 결정할 사항마다 "아직 안 다룸 / 미결 / 결정 / 결정 확인 필요"와 결정 내용 한 줄, 그렇게 본 근거 발언을 보여 준다. 안건 상태는 그 결과를 모아서 보여 준다 |
| 다루는 것 | 안건 보드 `agendas[].decisionPoints` 채우기, 안건 `status`·`statusReason` 정하기, 사람이 고친 결정 내용 받기 |
| 이 문서 밖 | 의견·할 일(AI-05), 주제 변경 감지(AI-06), 미결 안건 목록(AI-07), 오늘 회의 요약(AI-08). AI-07·AI-08은 이 문서의 값을 복사해서 담는다 |

## 2. 상태 값

### 2.1 결정할 사항의 상태 (`decisionPoints[].status`)

| 값 | 화면 표현 | 정하는 방법 |
|---|---|---|
| `NOT_STARTED` | 논의 전 | 그 사항을 다룬 줄이 없다 (모델이 "다룬 줄 없음"으로 판정하거나, 안건에 연결된 줄이 없다) |
| `UNDECIDED` | 미결 | 논의는 있었으나 결정이 없다. 모델이 아직 정해지지 않은 내용을 한 문장으로 쓴다 |
| `DECIDED` | 결정 | 모델이 "이 사항에 대한 답과 합의 표현이 있다"고 판정하고 결정 내용 한 줄과 근거 줄이 검증을 통과했다 |
| `DECISION_CHECK` | 결정 확인 필요 | 모델이 "답처럼 보이는 말은 있지만 확신이 낮다"고 판정하고 결정 후보 한 줄과 근거 줄이 검증을 통과했다 |

- 값 네 개와 칸 이름은 cn 팀이 요청한 모양이다(요청 2). `DECISION_CHECK`는 이 이름 그대로 받겠다는 답을 받았다.
- `DECIDED`, `DECISION_CHECK`는 근거 없이 내지 않는다. 문장이나 근거가 검증을 통과하지 못하면 그 사항은 결정으로 내지 않고 `UNDECIDED`로 낸다 (6장).
- 회의 중 화면은 결정·미결·논의 전 세 가지 색이어서, `DECISION_CHECK`를 회의 중에 따로 보일지는 기획 확인 필요다 (12장).

### 2.2 안건의 상태 (`agendas[].status`)

안건 상태는 **모델 없이** 사항 상태에서 정한다. 위에서부터 처음 맞는 줄을 쓴다.

| 번호 | 조건 | 안건 상태 | 화면 표현 |
|---|---|---|---|
| 1 | 안건에 연결된 줄이 없다 | `NOT_STARTED` | 아직 안 다룸 |
| 2 | 모든 사항이 `DECIDED` | `DECIDED` | 결정 |
| 3 | 모든 사항이 `DECIDED` 또는 `DECISION_CHECK`이고 `DECISION_CHECK`가 1개 이상 | `DECISION_CHECK` | 결정 확인 필요 |
| 4 | 그 밖: `UNDECIDED`나 `NOT_STARTED` 사항이 하나라도 있다 | 현재 안건이면 `DISCUSSING`, 아니면 `UNDECIDED` | 논의 중, 미결 |

- 결정할 사항이 3개인데 1개만 결정되어도 안건은 결정이 아니다. 기획팀 답은 "하나라도 결정이 아니면 미결"이다 (4번).
- **확인 필요한 해석**: 기획팀의 "미결로 본다"를 "다른 안건으로 넘어갔거나 회의가 끝난 뒤"로 읽었다. 논의가 진행 중인 현재 안건은 일부만 결정되어도 `DISCUSSING`으로 둔다. 진행 중에도 바로 미결로 보이길 원하는지는 기획 확인 필요다 (12장).
- 현재 안건이 바뀌면 이전 안건의 `DISCUSSING`은 `UNDECIDED`로 바뀐다. 회의가 끝나면 `DECIDED`, `DECISION_CHECK`가 아닌 줄 있는 안건은 모두 `UNDECIDED`이다.
- 안건 상태를 정할 때 `edited`, `needsCheck`는 보지 않는다. 사람이 고친 결정 내용이 있어도 AI의 사항 판정으로 정한다.
- 일부 사항은 결정이고 일부가 확인 필요이면 3번, 거기에 미결이 섞이면 4번이다. 이 방식은 AI 제안이다 (12장).
- 모델이 정하기 어려운 것은 "사항마다 결정이 났는가" 하나이고, 안건 상태는 그 결과와 현재 안건 정보로 정할 수 있어서 규칙으로 둔다.

## 3. 보드에 담기는 모양

기존 보드(`agenda-summary-contract.md` 4장)의 안건마다 `decisionPoints`가 늘어난다. `status`와 `statusReason`은 2.2의 규칙으로 채운다.

```json
{
  "agendaId": 101,
  "status": "UNDECIDED",
  "statusReason": {"text": "결정할 사항 3개 중 1개가 결정됨 (결정 확인 필요 1개, 미결 1개)", "evidenceSeqs": [43, 45, 51]},
  "decisionPoints": [
    {"decisionPointId": 7, "status": "DECIDED", "decisionText": "...", "evidenceSeqs": [42, 43], "edited": false, "needsCheck": false},
    {"decisionPointId": 8, "status": "DECISION_CHECK", "decisionText": "...", "evidenceSeqs": [45], "edited": false, "needsCheck": false},
    {"decisionPointId": 9, "status": "UNDECIDED", "decisionText": "...", "evidenceSeqs": [51], "edited": false, "needsCheck": false}
  ],
  "summary": [],
  "opinions": [],
  "todos": []
}
```

(`...`는 줄여 쓴 자리다. 전체 예시는 `examples/api/agenda-board-decision-points-put.json`)

### 3.1 decisionPoints의 항목

| 칸 | 타입 | 설명 |
|---|---|---|
| `decisionPointId` | 안건 목록에서 받은 값 | 결정할 사항 번호. **AI가 만들지 않고** 받은 값을 타입 그대로 돌려준다. 사용자가 문구를 고쳐도 번호는 유지된다 (cn 팀 답) |
| `status` | 문자열 | 2.1의 네 값 |
| `decisionText` | 문자열 | 결정 내용 한 줄. `DECIDED`는 결정된 내용, `DECISION_CHECK`는 결정으로 보이는 내용(후보), `UNDECIDED`는 아직 정해지지 않은 내용, `NOT_STARTED`는 고정 문구다 (6장). 사람이 고쳤으면(`edited`) 고친 글이다. 비어 있지 않다 |
| `evidenceSeqs` | 정수 배열 | 근거가 된 전사 줄 번호. **개수 상한 없이 모두** 담는다. **비어 있을 수 있다.** 비어 있으면 화면이 "근거가 부족해요"를 보인다 (기획팀 답: 근거 발언 0개일 때). `DECIDED`, `DECISION_CHECK`는 비어 있지 않다 |
| `edited` | 불리언 | 사람이 고친 결정 내용이면 `true` (7장) |
| `needsCheck` | 불리언 | "확인 필요" 표시. 고친 결정 내용의 근거가 달라졌을 때 `true` (7장). 안건 요약·의견·할 일의 `needsCheck`와 같은 뜻이다 |

- 담는 사항은 **그때 안건 목록에 있는 모든 사항**이다. 줄이 없는 안건도 모든 사항이 `NOT_STARTED`로 들어간다. 순서는 안건 목록의 `position` 순이다.
- 안건 목록에서 사라진 사항은 다음 보드에서 빠진다. 사항의 추가·삭제는 백엔드가 하고 안건 목록(`agenda-contract.md`)으로 알려 준다.
- `status`가 `DECIDED`인 사항이 있어도 안건이 미결일 수 있다 (2.2).

### 3.2 안건의 statusReason

- 줄이 없는 안건(`NOT_STARTED`)은 `null`이다.
- 그 밖의 안건은 `{text, evidenceSeqs}`이고 **코드가 만든 문장**이다. 모델이 쓰지 않는다. 문장은 사항 개수만 담는다 (예: "결정할 사항 3개 중 1개가 결정됨 (결정 확인 필요 1개, 미결 1개)"). 내용은 사항의 `decisionText`가 담는다.
- `evidenceSeqs`: 안건 상태가 `DECIDED`·`DECISION_CHECK`이면 `DECIDED`·`DECISION_CHECK` 사항들의 근거 줄을 합친 것이고, 그 밖이면 연결된 마지막 발언 줄 하나다 (v0.1과 같다).
- v0.1에서는 `DECIDED` 안건의 `statusReason`을 모델이 쓴 한 문장으로 썼다. 이제 결정 내용은 사항마다 `decisionText`로 간다. `statusReason`을 결정 문장 재료로 쓰던 곳(회의록 초안)은 `decisionPoints`를 읽어야 한다 (`agenda-today-summary-contract.md` 3.2).

## 4. 판정 시점

- 줄이 새로 붙은 안건은 새 줄이 2개 이상이면 바로, 1개면 60초(음성 시간) 뒤에 판정한다 (안건별 요약과 같은 규칙).
- 줄이 빠져나갔거나 글이 바뀐 안건(사람이 고친 분류 포함)은 기다리지 않고 바로 다시 판정한다.
- 결정(`DECIDED`, `DECISION_CHECK`)이 난 사항이 있는 안건도 새 줄이 오면 다시 판정한다.
- **안건 목록이 바뀌어 결정할 사항의 문구가 달라졌거나 사항이 늘거나 줄었으면** 그 안건을 기다리지 않고 바로 다시 판정한다. 번호가 같은 사항은 그 번호의 결과를 새 문구 기준의 결과로 바꾼다 (사람이 고친 결정 내용은 바꾸지 않는다. 7장).
- **사람이 결정 내용을 고치면** 그 안건을 다음 주기에 바로 다시 판정한다 (7장).
- 판정 호출은 **안건당 1번에 그 안건의 모든 사항**을 한꺼번에 판정한다. 사항마다 부르지 않는다.
- 회의가 끝나면(`end`) 바뀐 안건을 한 번 더 판정하고, 안건 상태를 확정한다 (2.2).
- 사용자가 회의 종료 버튼을 누르면(AI-07, `agenda-leftover-contract.md`) 새 줄이 1개일 때 기다리는 규칙을 한 번 건너뛰고 판정한다. 이때는 상태를 **확정하지 않는다**. 미결 안건 목록은 종료를 확정한다고 가정한 상태(논의 중인 안건은 미결)로 만들고 판정기의 상태는 바꾸지 않아서, 이어서 논의하기로 돌아가면 보드의 상태는 그대로 논의 중이다.
- 서버 안에서는 분류 → 상태 판정 → 안건별 요약 → 보드 전송 순서로 한 흐름에서 처리한다. 보드는 상태가 바뀔 때도 다시 보낸다.

## 5. 모델에 주는 입력

| 구분 | 내용 |
|---|---|
| 넣는 것 | 안건 제목, 결정할 사항 목록, 그 안건에 연결된 전사 줄(번호, 시각, 글) |
| 사항 번호 | 모델에는 사항마다 1부터 순번을 붙여 주고, 코드가 `decisionPointId`로 되돌린다. 모델은 번호를 만들지 않는다 |
| 맞장구 줄 | 합의 표현일 수 있어 넣는다. 안건 표시가 없으므로 바로 앞에 분류된 줄의 안건에 붙인다 (앞 줄 끝에서 10초 이내, 그 사이에 해당 없음 줄이 없을 때) |
| 빼는 것 | 간투사 줄, 분류하지 못한 줄, 안건별 요약 문장(요약 위에 쌓지 않는다) |
| 표시를 달아 넣는 것 (설정을 켠 경우만) | 낮은 확신도 줄은 `[불확실]` 표시를 달아 넣는다. 맞장구처럼 분류 대상이 아니라서, 바로 앞에 분류된 줄의 안건에 붙인다(앞 줄 끝에서 10초 이내, 그 사이에 해당 없음 줄이 없을 때). 모델은 뜻이 분명한 짧은 동의가 불확실 줄에만 있어도, 결정할 사항의 답이 불확실하지 않은 줄에 있으면 결정으로 낼 수 있고, 이때 문장에 "STT 불확실"을 밝힌다. 답 자체가 불확실 줄에만 있으면 결정 확인 필요로 낸다. 이 동작은 설정 `show_uncertain`을 켰을 때만 한다. **기본은 꺼짐**이라 낮은 확신도 줄은 예전처럼 뺀다(2026-10-23 전후 비교에서 효과가 확인되지 않아 기본을 껐다) |

## 6. 생성 문장과 검증

AI가 쓰는 문장은 사항마다 `decisionText` 하나이고, `DECIDED`·`DECISION_CHECK`·`UNDECIDED`일 때만 모델이 쓴다. 지어낼 위험이 가장 큰 것은 `UNDECIDED` 문장이다 (기획팀 답: 미결 문장도 AI가 쓴다).

| 규칙 | 내용 |
|---|---|
| 근거 필수 | `DECIDED`, `DECISION_CHECK`는 근거 줄이 1개 이상이어야 하고 모두 그 안건의 줄 번호 안에 있어야 한다 |
| `UNDECIDED` 문장 | 모델이 근거 줄을 함께 낸다. 근거가 그 안건의 줄 안에 있으면 그 줄들을, 근거를 내지 않았으면 빈 배열을 담는다 |
| 기존 검증기 | 문장은 요약과 같은 검증기(인용, 숫자, STT 불확실 표시)를 지난다 |
| 판단어 금지 | "우세하다", "다수", "대체로"처럼 대화에 없는 평가는 쓰지 않도록 프롬프트에서 금지한다 |
| 실패 처리 | 검증을 통과하지 못하면 오류를 알려 1회 더 부른다. 그래도 통과하지 못하면 그 사항은 결정으로 내지 않고 `UNDECIDED`로 두고 고정 문구를 쓴다 |
| 고정 문구 | `UNDECIDED`: "{결정할 사항 문구}는 아직 결정되지 않았어요". `NOT_STARTED`: "아직 논의되지 않았어요". 모델 없이 만든다. 고정 문구일 때 `evidenceSeqs`는 비어 있다 (제안) |
| 근거 줄 개수 | 상한이 없다. 프롬프트와 검증기에도 줄 개수 상한을 두지 않는다 |

- 호출이 연속 3번 실패하거나 회의당 호출 상한(기본 300)에 닿으면 이 회의의 **모델 판정만** 멈춘다. 이미 낸 사항 결과는 유지하고, 안건 상태는 그 결과에서 계속 정한다. 검증 탈락은 연속 실패로 세지 않는다.

## 7. 사람이 고친 결정 내용 받기 (백엔드 → ai-service)

사용자가 결정할 사항의 결정 내용을 직접 고치면(REQ-126, 회의록 작성자만) 백엔드가 바로 알린다. 주소와 본문은 cn 팀이 요청한 모양을 따른다.

```
POST /internal/meetings/{meetingId}/decision-edits
```

### 7.1 본문

| 필드 | 타입 | 설명 |
|---|---|---|
| `meetingId` | 문자열 또는 정수 | 주소의 값과 같아야 한다 |
| `edits` | 배열 | 고친 결정 내용. 한 번에 여러 개를 보낼 수 있다 |

### 7.2 edits의 항목

| 필드 | 타입 | 설명 |
|---|---|---|
| `agendaId` | 안건 번호 | 사항이 속한 안건 |
| `decisionPointId` | 사항 번호 | 고친 결정할 사항 |
| `decisionText` | 문자열 | 사용자가 고친 결정 내용. 비어 있으면 안 된다 |
| `evidenceSeqs` | 정수 배열 | 그 결정 내용의 근거 줄 번호. 백엔드가 저장한 값을 그대로 보낸다. 비어 있어도 된다 (제안) |
| `rev` | 정수 | 그 사항을 고칠 때마다 커지는 값. 시작값은 상관없고, 같은 `decisionPointId`는 `rev`가 큰 것만 반영한다 |

`action` 칸은 없다. 고친 요약(`agenda-summary-edits`)과 달리 "확인 필요를 확인함" 요청이 cn 팀 요청에 없다 (11장). `evidenceSeqs`를 함께 보내는 이유는 10장의 복구 때문이다. ai-service는 재시작하면 고친 내용을 모두 잃으므로, 다시 보낼 때 항목이 필요한 정보를 모두 갖고 있어야 한다.

### 7.3 ai-service의 처리

| 번호 | 규칙 |
|---|---|
| 1 | 받으면 그 사항의 `decisionText`와 `evidenceSeqs`를 그 값으로 고정하고 `edited`를 `true`로 한다. 이후 판정이 이 두 칸을 덮어쓰지 않는다 |
| 2 | 사항의 `status`는 AI가 계속 판정한다. 수정본은 그대로 두고 상태만 새로 낸다 |
| 3 | 고친 글은 사람이 쓴 글이므로 검증기를 거치지 않는다 |
| 4 | 고친 사항이 속한 안건은 다음 주기에 바로 다시 판정한다. 고친 글은 같은 안건의 다른 사항을 판정할 때 맥락으로만 쓴다 |
| 5 | 모르는 `decisionPointId`나 `agendaId`도 받아서 보관한다. 안건 목록이 늦게 도착한 경우일 수 있어서다 (`agenda-contract.md` 7.3 규칙 6과 같은 방식). 목록에 생기면 적용하고, 목록에서 사라진 사항·안건이면 버린다 |
| 6 | `needsCheck`를 켜는 조건은 셋이다. (가) 고친 사항의 근거 줄의 글이 바뀌었거나 줄이 사라졌다. (나) 근거 줄이 다른 안건으로 옮겨 갔다(분류가 바뀜). (다) **제안**: 사람이 결정 내용을 적었는데 AI의 새 판정이 `DECIDED`·`DECISION_CHECK`가 아니다. 끄는 조건은 사용자가 그 사항을 다시 고치는 것이다 |
| 7 | `rev`가 같거나 작아서 반영하지 않은 항목은 응답의 `ignored`에 담는다 |

### 7.4 응답

| 상황 | 응답 |
|---|---|
| 받음 | `200` + `{"accepted": true, "result": "accepted", "applied": 1, "ignored": []}`. `applied`는 새로 반영한 항목 수 |
| 모두 이미 반영된 `rev` | `200` + `{"accepted": true, "result": "stale", "applied": 0, "ignored": [{"decisionPointId": 7, "reason": "stale"}]}` |
| 끝난 회의 | `200` + `{"accepted": false, "result": "ignored", "reason": "ended"}` |
| 형식 오류, 주소와 본문의 `meetingId` 불일치, `decisionText`가 비어 있음 | `400` + `{"error": "INVALID_INPUT", "detail": "이유"}` |
| 아직 받을 수 없음 | `503` + `{"error": "NOT_READY", "detail": "이유"}` |

## 8. 설정

| 환경변수 | 설명 | 기본값 |
|---|---|---|
| `AGENDA_STATUS_REFRESH_SEC` | 새 줄이 1개뿐일 때 판정을 기다리는 시간(음성 시간 초) | 60 |
| `MAX_AGENDA_STATUS_CALLS_PER_MEETING` | 회의당 상태 판정 호출 상한 (비용을 추정한 뒤 다시 정함) | 300 |

모델은 요약과 같은 `LLM_PROVIDER`, `LLM_MODEL`을 쓴다. `LLM_PROVIDER=echo`이면 모델을 부르지 않는다. 새 환경변수는 없다.

## 9. 토큰 지표

모델 호출은 `ai.task=agenda_status`로 `gen_ai.client.token.usage`에 남는다. 사항 문장도 같은 호출에서 함께 만들어서 새 `ai.task` 값은 없다.

## 10. 복구

ai-service는 회의 상태를 메모리에만 둔다. 재시작하면 판정 결과와 고친 결정 내용이 모두 사라진다.

| 순서 | 내용 |
|---|---|
| 1 | 재시작 직후 모르는 회의의 줄 묶음이 오면 `409` + `{"expectedBatch": 1}`로 답한다 (`input-contract.md` 8장) |
| 2 | 백엔드는 줄 묶음을 1번부터 다시 보내기 전에 아래 순서로 먼저 보낸다: 안건 목록(참석자 명단 포함), 고친 분류, 고친 요약, 고친 의견·할 일, **고친 결정 내용(`decision-edits`, 고친 항목 전체)**, 무시 기록. 고친 결정 내용의 `rev`는 마지막 값이고 `decisionText`, `evidenceSeqs`는 백엔드가 저장한 값이다 |
| 3 | ai-service는 안건 목록을 받은 뒤 고친 결정 내용을 되살리고, 다시 받은 줄을 분류하고 판정한다. 고친 사항은 고정되어 있으므로 사람의 수정은 유지된다. 고치지 않은 사항은 다시 받은 줄로 새로 판정한다 |

## 11. 이번 범위에서 하지 않는 것

| 항목 | 이유 |
|---|---|
| 사람이 안건 상태나 사항 상태를 직접 고치기 | PRD와 요구사항에 없다. 받는 것은 결정 내용 문장뿐이다 (7장). 필요해지면 백엔드가 고친 값을 먼저 확인한다 |
| 고친 결정 내용에 대한 "확인함"(`confirm`) | cn 팀 요청에 없다. `needsCheck`는 사용자가 다시 고칠 때만 꺼진다 (7.3의 6번). 필요하면 `action`을 추가한다 |
| 결정할 사항 추가·삭제·번호 발급 | 백엔드 몫이다. AI는 안건 목록의 사항을 받아서 쓴다 |
| 회의가 끝난 뒤 "이어서 논의하기"(REQ-084) 처리 | AI-07의 종료 버튼 알림(`end-requests`)으로 대신한다 (`agenda-leftover-contract.md`) |
| 안건 여러 개에 걸친 결정 | 줄은 안건 하나에만 연결된다 |
| 모델에 요약 문장 주기 | 요약의 오류가 판정으로 번지는 것을 피한다 |

## 12. 협의 상태

| 항목 | 상태 |
|---|---|
| 안건 목록의 결정할 사항 `decisionPoints[{decisionPointId, position, text}]` | cn 팀 요청 (확정 모양). 계약은 `agenda-contract.md` 4.2 |
| 보드 안건마다 `decisionPoints[{decisionPointId, status, decisionText, evidenceSeqs, edited, needsCheck}]`, `status` 네 값 | cn 팀 요청 (확정 모양) |
| `decision-edits` 주소와 본문 | cn 팀 요청 (확정 모양). `evidenceSeqs`가 빈 배열이어도 되는지는 cn 팀 확인 필요 |
| 결정할 사항 번호는 문구를 고쳐도 유지되고, 사항이 0개인 안건은 없다 | cn 팀 답 |
| 사람이 고친 결정 내용은 고정한다 | cn 팀 요청 |
| 사항 `status`의 `evidenceSeqs`를 빈 배열로 보낸다 (근거 발언 0개 = "근거가 부족해요") | 기획팀 답. cn 팀 확인 필요 (빈 배열 허용) |
| 일부 사항만 결정이면 안건은 미결 | 기획팀 답 |
| 진행 중인 현재 안건은 일부만 결정되어도 `DISCUSSING`으로 둔다 | AI 해석, 기획팀 확인 필요 |
| 사항이 `DECIDED`·`DECISION_CHECK`뿐이고 `DECISION_CHECK`가 있으면 안건은 `DECISION_CHECK`, 미결이 섞이면 `UNDECIDED` | AI 제안, 기획팀 확인 필요 |
| 미결 사항 문장도 AI가 쓴다 (근거 필수, 검증, 탈락 시 고정 문구) | 기획팀 답. 고정 문구의 글은 AI 제안 |
| 고친 결정 내용의 `needsCheck` 조건 (가)(나)(다), 끄는 방법 | AI 제안, cn 팀 확인 필요 |
| 안건의 `statusReason`을 코드가 만든 문장(사항 개수)으로 바꾼다 | AI 제안, cn 팀 확인 필요 (저장·표시 계획) |
| `DECISION_CHECK`를 회의 중에 따로 보일지 (질문 3) | 기획팀 확인 필요 |
| 회의 종료 시 결정이 아닌 안건은 `UNDECIDED` | AI 제안 (v0.1과 같다) |
| 판정 시점(새 줄 2개 또는 60초), 호출 상한 300, 맞장구 붙이는 간격 10초 | 제안값, 평가 뒤 조정 |
