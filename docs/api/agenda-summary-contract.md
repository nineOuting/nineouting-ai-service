# AI 서버 안건 요약 형식 (AI-03) v0.1 초안

> 안건별 요약(AI-03)을 안건 보드(연동 API 초안 3.2)에 담아 보내는 방식과, 사람이 고친 요약을 받는 방식을 다룬다. 아직 cn 팀과 확인하기 전의 AI 쪽 제안이다. 확정되면 이 문서를 최신 전체본 하나로 교체한다.
> 안건 목록과 줄별 분류는 `agenda-contract.md`, 전사 줄을 받는 형식은 `input-contract.md`, 회의 중 주기 요약은 `output-contract.md`에 있다.

- 근거: PRD v0.1 AI-03, 요구사항 REQ-075, 연동 API 초안 3.2 (안건 보드 결과)
- 예시 파일: `examples/api/` (아래 12장)

## 1. 목적과 범위

| 구분 | 내용 |
|---|---|
| 목적 | 흐름을 놓친 참여자가 화면만 보고 따라잡도록, 안건마다 2~3줄 요약과 문장별 근거를 보여 준다 |
| 다루는 것 | 안건 보드의 `summary` 칸 채우기, 사람이 고친 요약 받기 |
| 요약 범위 | 등록된 모든 안건을 각각 요약한다. "현재 안건"은 별도 요약을 만들지 않고, 보드의 `currentAgendaId`로 화면에서 강조한다 |
| 이 문서 밖 | 안건 상태 판정(AI-04), 의견·할 일(AI-05), 주제 변경 감지(AI-06), 오늘 회의 요약(AI-08) |

AI-08은 새로 요약하지 않고 이 요약을 모아 배치한다. 그래서 이 문서의 근거 연결 정보(`evidenceSeqs`)와 사람이 고친 표시(`edited`, `needsCheck`)가 AI-08까지 그대로 이어진다.

## 2. 흐름

| 번호 | 내용 | 보내는 쪽 | 받는 쪽 | 방식 | 보내는 때 |
|---|---|---|---|---|---|
| 1 | 안건 보드 (요약 포함) | ai-service | 백엔드 | `PUT {백엔드 주소}/internal/meetings/{meetingId}/agenda-board` | 담을 값이 바뀔 때, 최대 초당 1번 |
| 2 | 사람이 고친 요약 | 백엔드 | ai-service | `POST /internal/meetings/{meetingId}/agenda-summary-edits` | 안건 보드에서 고칠 때 바로 |

- 1번의 주소와 "바뀔 때마다 전체 상태를 보낸다", "최대 초당 1번"은 연동 API 초안 3.2와 7장 4번을 따른다.
- 2번은 받으면 바로 응답하고, 반영은 뒤에서 한다 (`agenda-contract.md` 2장과 같은 방식).
- 1번은 요약·분류 결과 전송과 같은 백엔드 주소(`BACKEND_BASE_URL`)와 같은 재시도 규칙을 쓴다.

## 3. 공통 규칙

| 규칙 | 내용 |
|---|---|
| 필드 이름 | camelCase |
| `meetingId` | 주소에 있다. 2번 요청은 본문의 값이 주소와 다르면 `400` |
| `agendaId` | 안건 목록에서 받은 값을 타입 그대로 돌려준다 (연동 API 초안 공통 규칙은 숫자) |
| 근거 | `evidenceSeqs`는 근거가 된 전사 줄의 `seq`이다. 안건 보드의 `opinions[].evidenceSeqs`와 같은 방식이다. 시간 구간은 백엔드가 저장한 전사에서 알 수 있다 |
| `seq` | `input-contract.md`의 `lines[].seq`와 같다. 식별용 번호이고 시간 순서가 아니다 |

## 4. 안건 보드 보내기 (ai-service → 백엔드)

**전체 상태**를 보낸다. 안건 목록에 있는 모든 안건을 담고, 백엔드는 받은 상태로 통째로 바꾼다. 순서가 뒤바뀌어 도착해도 `version`으로 거른다 (연동 API 초안 3.2와 같다).

### 4.1 본문

| 필드 | 타입 | 설명 |
|---|---|---|
| `version` | 정수 | 회의 안에서 계속 커진다. 4.5 규칙 |
| `basedOnSeq` | 정수 | 이 상태에 반영한 전사 줄 중 가장 큰 `seq`. 어디까지 보고 만든 결과인지를 뜻한다 |
| `currentAgendaId` | 안건 번호 또는 null | 지금 논의 중인 안건. 줄별 분류 결과(`agenda-classification`)의 `currentAgendaId`와 같은 값이다. 아직 연결된 줄이 없으면 `null` |
| `agendas` | 배열 | 안건 목록의 모든 안건. 항목은 4.2 |
| `offTopic` | 객체 또는 null | 주제 변경 감지(AI-06). 제안이 떠 있을 때만 객체이고 아니면 `null`. 모양은 `agenda-offtopic-contract.md` 3장 |
| `leftover` | 객체 또는 null | 미결 안건 추출(AI-07). 종료 버튼 요청을 받았거나 회의가 끝났을 때만 객체이고 아니면 `null`. 모양은 `agenda-leftover-contract.md` 3장 |
| `todaySummary` | 객체 또는 null | 오늘 회의 요약 정리본(AI-08). `leftover`와 같은 시점에 객체이고 아니면 `null`. 안건마다 상태, 판정 근거, 요약 문장, 의견, 할 일을 묶은 사본이다. 모양은 `agenda-today-summary-contract.md` 3장 |

### 4.2 agendas의 항목

| 필드 | 타입 | 설명 |
|---|---|---|
| `agendaId` | 안건 번호 | 안건 목록의 값 |
| `status` | 문자열 | 안건 상태 판정(AI-04). 값과 `statusReason`은 `agenda-status-contract.md` |
| `summary` | 배열 | 그 안건의 요약 문장 전체. 항목은 4.3. 비어 있으면 보여 줄 요약이 없다는 뜻이다 |
| `decisionPoints` | 배열 | 결정할 사항마다 상태, 결정 내용, 근거(AI-04). 안건 목록의 모든 사항이 들어 있다. 항목은 `agenda-status-contract.md` 3.1. 안건의 `status`는 이 값에서 정한다 |
| `opinions` | 배열 | 의견·근거(AI-05) 구현 전까지 빈 배열 |

연동 API 초안 3.2의 `summary`는 문자열이었다. 문장마다 근거를 연결하고 사람이 고친 문장을 구분하려고 문장 목록으로 바꾼다 (11장).

### 4.3 summary의 항목

| 필드 | 타입 | 설명 |
|---|---|---|
| `id` | 문자열 | 문장 번호. 뜻이 없는 문자열이며 회의 안에서 겹치지 않는다. 재시작 뒤에도 겹치지 않게 만든다. 사람이 고친 문장은 갱신해도 같은 번호를 유지한다 |
| `text` | 문자열 | 요약 한 줄 |
| `evidenceSeqs` | 정수 배열 | 근거가 된 전사 줄 번호. 1개 이상 |
| `edited` | 불리언 | 사람이 고친 문장이면 `true`. 고친 문장은 갱신해도 바꾸지 않는다 (6장) |
| `needsCheck` | 불리언 | "확인 필요" 표시. 고친 문장의 근거가 달라졌을 때 `true` (6장) |

- 근거(`evidenceSeqs`)가 없는 문장은 만들지도 보내지도 않는다 (PRD AI-03).
- 문장은 근거 줄의 시작 시각 순으로 담는다.
- `summary`가 빈 배열인 경우: 요약할 줄이 아직 없거나 없어졌다(줄이 다른 안건으로 옮겨 감). 화면에서 "아직 안 다룸" 같은 상태를 보여 주는 것은 AI-04이며 `agenda-status-contract.md`에서 정한다.
- 안건당 문장 수는 최대 3개이다 (제안, 평가 뒤 조정). 사람이 고친 문장이 먼저 자리를 차지한다.

### 4.4 보내는 때

- 담을 값(안건별 요약, 현재 안건)이 마지막으로 보낸 것과 달라졌을 때 보낸다. 같으면 보내지 않는다.
- 안건이 추가·삭제되어 담을 안건이 달라졌을 때도 보낸다. 안건 목록을 아직 받지 못했으면 보내지 않는다.
- 보내는 횟수는 최대 초당 1번이다 (연동 API 초안 7장 4번). 요약은 약 1분 주기로 갱신하므로 실제로는 훨씬 드물다.
- 회의 `end` 알림을 처리하면서 요약이 바뀌었으면 마지막 상태를 보낸다. 연동 API 초안 3.2에는 `final` 칸이 없으므로, 백엔드는 가장 큰 `version`을 최종으로 본다.

### 4.5 version 규칙

- 같은 회의에서 보낼 때마다 커진다.
- 시각(밀리초) 이상의 값으로 시작해서, ai-service가 재시작해도 이전에 보낸 값보다 작아지지 않는다 (`output-contract.md` 4장과 같다).
- 백엔드는 이미 받은 값보다 작거나 같은 `version`을 버린다.

### 4.6 응답과 재시도

응답은 `204`이다. 재시도 규칙은 `output-contract.md` 5장과 같다.

| 백엔드 응답 | ai-service의 동작 |
|---|---|
| `2xx` | 성공 |
| `408`, `429`, `5xx`, 연결 오류 | 재시도 3회, 간격 1초·2초·4초 |
| 그 밖의 `4xx` | 다시 보내도 소용없으므로 포기하고 로그에 남긴다 |

전체 상태를 보내므로, 재시도하는 사이에 더 새 상태가 생기면 옛것은 다시 보내지 않고 새것을 보낸다. 모두 실패해도 다음에 상태가 바뀔 때 전체 상태를 다시 보낸다.

## 5. 사람이 고친 요약 받기 (백엔드 → ai-service)

사용자가 안건 보드에서 요약 문장을 고치거나, "확인 필요" 표시를 확인했다고 표시하면 백엔드가 바로 알린다.

### 5.1 본문

| 필드 | 타입 | 설명 |
|---|---|---|
| `meetingId` | 문자열 또는 정수 | 주소의 값과 같아야 한다 |
| `edits` | 배열 | 고친 문장. 한 번에 여러 개를 보낼 수 있다 |

### 5.2 edits의 항목

| 필드 | 타입 | `edit` | `confirm` | 설명 |
|---|---|---|---|---|
| `agendaId` | 안건 번호 | 필수 | 필수 | 문장이 속한 안건 |
| `itemId` | 문자열 | 필수 | 필수 | 4.3의 문장 번호 |
| `action` | 문자열 | 필수 | 필수 | `"edit"`(문장을 고침) 또는 `"confirm"`(확인 필요를 확인함) |
| `text` | 문자열 | 필수 | 없음 | 사용자가 고친 문장. 비어 있으면 안 된다 |
| `evidenceSeqs` | 정수 배열 | 필수 | 없음 | 그 문장의 근거 줄 번호. 백엔드가 저장한 값을 그대로 보낸다 |
| `rev` | 정수 | 필수 | 필수 | 그 문장을 고치거나 확인한 횟수. 올라갈 때마다 커지면 되고 시작값은 상관없다. 같은 `itemId`는 `rev`가 큰 것만 반영한다 |

`edit`에 근거를 함께 보내게 한 이유는 9장의 복구 때문이다. ai-service는 재시작하면 문장을 모두 잃으므로, 백엔드가 고친 문장을 다시 보낼 때 문장이 자기 안에 필요한 정보를 모두 갖고 있어야 한다.

### 5.3 ai-service의 처리

| 번호 | 규칙 |
|---|---|
| 1 | `edit`을 받으면 그 문장을 고정한다. `text`를 그 글로 바꾸고 `edited`를 `true`로 한다. 이후 갱신에서 다시 생성하거나 덮어쓰지 않는다 |
| 2 | 고친 문장은 사람이 쓴 글이므로 근거 검증기(인용·숫자·STT 불확실 표시)를 거치지 않는다 |
| 3 | `itemId`를 모르는 `edit`은 새 고정 문장으로 만들어 그 안건에 넣는다. 재시작 뒤 복구(9장)이거나, 사용자가 고치는 사이에 AI가 그 문장을 새로 만든 문장으로 바꾼 경우이다. 뒤의 경우에는 비슷한 문장이 둘 생길 수 있다 |
| 4 | `confirm`을 받으면 그 문장의 `needsCheck`를 `false`로 한다. 문장은 고정된 채로 남는다. 고치지 않은 문장에 대한 `confirm`은 무시한다 |
| 5 | 고쳤거나 확인한 안건은 다음 요약 주기에 바로 다시 요약한다 (7장). 고친 문장은 같은 안건의 다른 문장을 만들 때 맥락과 "다시 쓰지 말 것"으로만 쓴다 |
| 6 | 안건 목록에 없는 `agendaId`도 받아서 보관한다. 안건 목록이 늦게 도착한 경우일 수 있어서다 (`agenda-contract.md` 7.3과 같은 방식). 목록에서 사라진 안건이면 8장대로 버린다 |
| 7 | `rev`가 같거나 작아서 반영하지 않은 항목은 응답의 `ignored`에 담는다 |

### 5.4 응답

| 상황 | 응답 |
|---|---|
| 받음 | `200` + `{"accepted": true, "result": "accepted", "applied": 2, "ignored": []}`. `applied`는 새로 반영한 항목 수 |
| 모두 이미 반영된 `rev`이거나 무시된 항목 | `200` + `{"accepted": true, "result": "stale", "applied": 0, "ignored": [{"itemId": "...", "reason": "stale"}]}` |
| 형식 오류, 주소와 본문의 `meetingId` 불일치, `edit`에 `text`·`evidenceSeqs`가 없음 | `400` + `{"error": "INVALID_INPUT", "detail": "이유"}` |
| 아직 받을 수 없음 | `503` + `{"error": "NOT_READY", "detail": "이유"}` |

`ignored`의 `reason`은 `"stale"`(`rev`가 오래됨), `"not_edited"`(고치지 않은 문장에 대한 `confirm`)이다.

## 6. ai-service의 요약 규칙

| 번호 | 규칙 |
|---|---|
| 1 | 요약 대상 줄은 분류 결과가 안건인 줄이다. 해당 없음 줄, 분류 대상이 아닌 줄(맞장구, 간투사, 낮은 확신도)은 뺀다. 사람이 고쳐서 고정된 분류는 그대로 믿고 쓴다 |
| 2 | 안건마다 그 안건의 줄만 보고 2~3줄로 요약한다. 안건 제목과 결정할 사항을 함께 보여 주되, 줄에 없는 내용을 제목에서 가져와 쓰지 않는다 |
| 3 | 요약 위에 요약을 쌓지 않는다. 갱신할 때마다 그 안건의 원문 줄에서 새로 만든다. 앞서 만든 문장은 맥락을 이해하는 데만 쓰고 근거로 쓰거나 베끼지 않는다 |
| 4 | 모든 문장은 근거 줄이 있어야 한다. 인용, 숫자, STT 불확실 표시를 검증기로 확인하고 통과하지 못한 문장은 보내지 않는다. 지어낸 숫자와 고유명사를 만들지 않는다 |
| 5 | 사람이 고친 문장은 갱신하지 않는다 (5.3의 1번) |
| 6 | `needsCheck`는 고친 문장에 대해서만 켠다. 켜는 조건은 둘이다. (가) 근거 줄의 글이 바뀌었거나 줄이 사라졌다. (나) 근거 줄이 다른 안건으로 옮겨 갔다(분류가 바뀜). 끄는 조건은 `confirm`을 받거나, 사용자가 문장을 다시 고치는 것이다 |
| 7 | 고친 뒤에 쌓인 발언의 의미가 고친 문장과 달라지는 경우는 이번 단계에서 감지하지 않는다. 결정할 수 있는 규칙(6번의 두 조건)만 구현한다 |
| 8 | 로그와 상태 조회에 전사 내용, 안건 제목, 요약 문장을 남기지 않는다. 회의 번호, 개수, 예외 이름만 남긴다 |

## 7. 갱신 시점

값은 모두 제안이며 평가 뒤에 조정한다.

| 번호 | 규칙 |
|---|---|
| 1 | 분류 호출이 끝난 직후, 같은 처리 흐름에서 요약 단계를 이어서 돈다. 두 단계가 서로 다른 시점의 분류를 보지 않게 하려는 것이다 |
| 2 | 새 줄이 붙은 안건만 다시 요약한다 |
| 3 | 새 줄이 2개 이상이면 바로, 1개이면 최대 60초(음성 시간)까지 기다렸다가 요약한다 |
| 4 | 분류가 바뀌어 줄을 잃거나 얻은 안건, 사람이 분류를 고친 줄이 속한 안건, 사람이 요약을 고치거나 확인한 안건은 3번의 기다림 없이 다음 주기에 요약한다 |
| 5 | 회의 `end` 알림을 처리한 뒤 모든 안건을 마지막으로 한 번 요약하고, 바뀐 것이 있으면 보낸다 |
| 6 | 요약 호출이 실패해도 분류와 다른 안건을 막지 않는다. 연속 3번 실패하면 그 회의의 요약을 멈추고, 회의당 호출 횟수 상한을 둔다. 상한 값은 비용을 추정한 뒤 정한다 |

갱신 지연 목표는 PRD 9장의 1분 이내(제안값)이다. 분류 호출 주기(30초)와 요약 호출 시간(수 초)을 더하면 들어올 것으로 추정하지만, 이 문서에서 약속하지 않는다. 평가에서 재서 알린다.

## 8. 분류가 나중에 바뀔 때

분류는 새 줄이 올 때뿐 아니라 안건 변경·삭제나 사람의 수정으로도 바뀐다 (`agenda-contract.md` 8장).

| 상황 | 요약의 처리 |
|---|---|
| 줄이 안건 A에서 안건 B로 옮겨 감 | 최신 분류 기준으로 A와 B를 각각 원문 줄에서 다시 요약한다. 이미 만든 요약을 고쳐 쓰지 않는다 |
| 고친 문장의 근거 줄이 다른 안건으로 옮겨 감 | 문장은 그대로 두고 `needsCheck`를 켠다 (6장 6번) |
| 안건이 삭제됨 | 그 안건의 요약 상태를 지운다. 고친 문장도 함께 지운다. 안건 보드는 전체 상태이므로 목록에서 빠진 안건은 다음 상태에 담기지 않는다. 삭제를 따로 알리는 필드는 두지 않는다 |
| 안건의 제목·결정할 사항이 바뀜 | 이미 만든 요약은 다시 만들지 않는다. 다음에 그 안건이 갱신될 때부터 새 제목을 기준으로 한다 |

## 9. 복구

ai-service는 회의 상태를 메모리에만 둔다. 재시작하면 안건 목록, 분류, 요약 문장이 모두 사라진다.

| 순서 | 내용 |
|---|---|
| 1 | 재시작 직후 모르는 회의의 줄 묶음이 오면 `409` + `{"expectedBatch": 1}`로 답한다 (`input-contract.md` 8장) |
| 2 | 백엔드는 줄 묶음을 1번부터 다시 보내기 전에 최신 안건 목록, 고친 분류 전체(`agenda-contract.md` 9장)에 더해 **사람이 고친 요약 문장 전체**를 `agenda-summary-edits`로 다시 보낸다. 문장마다 `action`은 `"edit"`, `rev`는 마지막 값이고 `text`, `evidenceSeqs`는 백엔드가 저장한 값이다 |
| 3 | ai-service는 안건 목록을 받은 뒤 고친 문장을 되살리고, 다시 받은 줄을 분류하고 요약한다. 고친 문장은 고정되어 있으므로 사람의 수정은 유지된다 |

- 고치지 않은 문장은 다시 보내지 않는다. 줄을 다시 받으면 AI가 새로 만든다.
- 되살린 문장의 근거 줄이 다시 분류된 결과와 어긋나면 6장 6번에 따라 `needsCheck`가 켜진다.
- 안건 보드의 `version`은 시각 기반이라 재시작 전보다 작아지지 않는다.

## 10. 이번 범위에서 하지 않는 것

PRD에 없는 기능이라 제안만 하고 구현하지 않는다.

| 항목 | 이유 |
|---|---|
| 사람이 고친 문장의 잠금 해제, 문장 삭제, 새 문장 추가 | PRD AI-03은 "수정"만 정한다. 필요하면 기획 확인 뒤 `action`을 늘린다 |
| 고친 뒤 쌓인 발언의 의미가 달라진 것을 감지 | 결정할 수 있는 규칙이 없다. 이번에는 근거가 달라진 경우만 감지한다 (6장 7번) |
| 현재 안건 별도 요약 | 안건별 요약을 화면에서 강조하는 것으로 대신한다 (1장) |
| `opinions`, `offTopic` 채우기 | 각각 AI-05(`agenda-opinions-contract.md`), AI-06(`agenda-offtopic-contract.md`)이 채운다. 채울 것이 없으면 빈 배열, `null`로 보낸다. `status`와 `decisionPoints`는 AI-04(`agenda-status-contract.md`)가 채운다 |
| 사전 자료 반영 | 추후 지원 예정 (`agenda-contract.md` 10장) |

### 11.1 안건 보드(연동 API 초안 3.2)와의 관계

AI-02·03·04·05·06의 결과가 모두 안건 보드로 모이도록, 어디에 무엇이 가는지 정리한다.

| 내용 | 가는 곳 | 구현 시점 |
|---|---|---|
| 줄별 분류 (`seq` → `agendaId`) | `agenda-classification` (별도 주소, 줄 단위라 보드에 담지 않는다) | AI-02 |
| 현재 안건 | 보드 `currentAgendaId` (분류 결과에도 같은 값이 간다. 화면은 보드의 값을 쓴다) | AI-02 |
| 안건별 요약 | 보드 `agendas[].summary` | AI-03 |
| 안건 상태와 판정 근거 | 보드 `agendas[].status`, `statusReason` (`agenda-status-contract.md`). 안건 상태는 사항 상태에서 정한다 | AI-04 |
| 결정할 사항별 상태·결정 내용·근거 | 보드 `agendas[].decisionPoints` (`agenda-status-contract.md` 3.1) | AI-04 |
| 의견·근거 | 보드 `agendas[].opinions` | AI-05 |
| 주제 변경 | 보드 `offTopic` | AI-06 |
| 미결 안건 목록과 논의 요약 | 보드 `leftover` (`agenda-leftover-contract.md`) | AI-07 |
| 오늘 회의 요약 정리본 | 보드 `todaySummary` (`agenda-today-summary-contract.md`) | AI-08 |

연동 API 초안 3.2와 다른 점은 `summary`의 형식 하나이다. 나머지 칸은 초안을 그대로 쓴다.
