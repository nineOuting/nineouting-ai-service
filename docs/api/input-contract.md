# AI 서버 입력 형식 (백엔드 → ai-service) v0.1 초안

> 설계 가정 v0.1 기준. 클라우드 팀과 협의 중인 초안이다. 확정되면 이 문서를 최신 전체본 하나로 교체한다.

- 근거: STT 레포의 `prototype/app/backend_sender.py`(STT → 백엔드 형식, 2026-10-15 확정), 백엔드의 전달 요청(2026-10-16)
- 예시 파일: `examples/api/` (아래 10장)

## 1. 목적과 범위

| 구분 | 내용 |
|---|---|
| 목적 | 백엔드가 확정된 전사 줄과 사용자의 수정·삭제·추가분을 ai-service에 넘기는 형식을 정한다 |
| 쓰는 곳 | 회의 중 안건 요약(AI-03)과 이후 기능의 공통 입력 |
| 이 문서 밖 | STT → 백엔드 형식, 사전 자료 전달. 안건 목록과 사람이 고친 분류를 받는 형식은 `agenda-contract.md`. AI 결과를 돌려주는 형식은 `output-contract.md` |

## 2. 흐름

| 구간 | 보내는 쪽 | 받는 쪽 | 주기 |
|---|---|---|---|
| 소리 | 브라우저 | STT 서버 | 실시간 (WebSocket) |
| 전사 줄 | STT 서버 | 백엔드 | 0.5초 |
| 회의 알림 | 백엔드 | ai-service | 생길 때 바로 |
| 줄 묶음 | 백엔드 | ai-service | 10초. 보낼 것이 없으면 보내지 않는다 |

백엔드가 ai-service로 보내는 방식(밀어 주기)을 AI 쪽이 희망한다. 받는 주소와 HTTP 방식은 백엔드 초안에 맞춘다.

## 3. 공통 규칙

| 규칙 | 내용 |
|---|---|
| 필드 이름 | camelCase |
| 시간 단위 | 정수 밀리초 |
| 음성 시각 | `startMs`, `endMs`, `atMs`는 회의 시작 기준 음성 시간이다. 멈춘 동안은 늘지 않는다 |
| 실제 시각 | 회의 알림의 `wall`로 계산한다. ISO 8601, `+09:00` 표기 |
| `meetingId` | 문자열 (예: `"m_1234"`) |
| 줄 순서 | `startMs` 기준이다. `seq`는 식별용이며 시간 순서가 아니다. 보완 줄은 이미 보낸 줄보다 앞 시각으로 올 수 있다 |
| 같은 줄의 버전 | 같은 `seq`는 `rev`가 가장 큰 것만 반영한다 |

## 4. 회의 알림

시작·멈춤·재개·종료가 생기면 바로 보낸다.

| 필드 | 타입 | 설명 |
|---|---|---|
| `meetingId` | 문자열 | |
| `event` | 문자열 | `start`, `pause`, `resume`, `end` |
| `atMs` | 정수 | 그 시점의 음성 시각 |
| `wall` | 문자열 | 실제 시각 |

| 알림 | ai-service의 동작 |
|---|---|
| `start` | 새 회의 상태를 만든다 |
| `pause` | 진행 중이던 구간을 마감한다 |
| `resume` | 이어서 받는다. `atMs`는 `pause`의 값에서 이어진다 |
| `end` | 마지막 구간을 마감하고 종료 시점 요약을 만든다 |

`end`는 마지막 줄 묶음을 보낸 뒤에 보낸다. 순서가 바뀌면 마지막 구간의 줄이 빠진다.

## 5. 줄 묶음

10초마다 보낸다. 그사이 새로 확정된 줄(`lines`)과 이미 보낸 줄의 변경(`edits`)을 담는다.

| 필드 | 타입 | 설명 |
|---|---|---|
| `meetingId` | 문자열 | |
| `batch` | 정수 | 회의마다 1부터 1씩 늘어나는 묶음 번호. 줄 번호 `seq`와 다르다 |
| `lines` | 배열 | 새로 확정된 줄 |
| `edits` | 배열 | 이미 보낸 줄의 수정·삭제 |

### 5.1 lines의 항목

| 필드 | 타입 | 설명 |
|---|---|---|
| `seq` | 정수 | 줄 번호 |
| `startMs`, `endMs` | 정수 | 음성 시각. `endMs`가 null이나 없음으로 오면 `startMs`와 같은 값으로 처리한다 |
| `text` | 문자열 | 전사 글 |
| `kind` | 문자열 또는 null | `"backchannel"`(맞장구), `"filler"`(간투사), `null`(일반 발언) |
| `lowConfidence` | 불리언 | 글자(공백 제외)의 20% 이상이 확신도 0.3 미만이면 `true`. 사용자가 고친 줄은 `false` |
| `recovered` | 불리언 | 스트리밍이 놓친 말을 다시 인식해 채운 보완 줄 |
| `manual` | 불리언 | 사용자가 직접 추가한 줄. 아직 요구사항에 없어서 항상 `false`이고 이런 줄은 오지 않는다 |

`lines`는 확정된 줄만 담으므로 `final` 필드는 없다.

### 5.2 edits의 항목

| 필드 | 타입 | 설명 |
|---|---|---|
| `seq` | 정수 | 고친 줄의 번호 |
| `rev` | 정수 | 변경 번호. 1부터 시작하지 않고 줄마다 이어서 매긴다. 예: STT 확정이 2였다면 사용자 수정은 3 |
| `text` | 문자열 | 사용자가 고친 글 (수정일 때) |
| `deleted` | 불리언 | `true`이면 삭제 |
| `speakerLabel` | 문자열 | 보내지 않는다 (STT가 2026-10-16에 발화자 구분을 하지 않기로 했다). 오더라도 ai-service는 쓰지 않는다 |

## 6. ai-service의 처리 규칙

| 번호 | 규칙 |
|---|---|
| 1 | 요약 입력에서 `lowConfidence`가 `true`인 줄과 `kind`가 `backchannel`·`filler`인 줄을 뺀다 |
| 2 | 사용자가 고친 줄과 직접 추가한 줄(`manual`)은 사람이 의도해서 적은 글이므로 일반 발언으로 보고 요약에 쓴다 (v0.1) |
| 3 | `seq`가 이미 삭제된 줄은 무시한다. 아직 받지 못한 `seq`의 수정은 보관했다가 그 줄이 오면 적용한다 (구현됨) |
| 4 | 늦게 온 줄은 `startMs` 위치에 끼워 넣고, 그 줄이 속한 구간을 다시 요약한다 |
| 5 | 이미 받은 `batch` 번호는 무시한다. 다음 번호(마지막+1)가 아니면 처리하지 않고 `409` + `expectedBatch`로 답해 그 번호부터 다시 받는다 |
| 6 | 줄마다 단어 단위 불확실 표시(`textMarked`)는 받지 않는다. 불확실성은 줄 단위 `lowConfidence`로만 다룬다 |

## 7. 응답

| 상황 | 응답 |
|---|---|
| 형식을 확인하고 받음 | `200` + `{"accepted": true, "result": "accepted", "batch": 7}`. 요약은 뒤에서 처리한다 |
| 이미 받은 `batch` 번호 | `200` + `{"accepted": true, "result": "duplicate"}`. 다시 보내지 않아도 된다 |
| `end` 이후에 온 묶음 | `200` + `{"accepted": false, "result": "ignored", "reason": "ended"}` |
| `batch` 번호가 이어지지 않음 | `409` + `{"expectedBatch": N}`. 처리하지 않는다. 백엔드가 N번부터 보냈던 그대로 다시 보낸다 |
| 형식 오류, 주소와 본문의 `meetingId` 불일치 | `400` + `{"error": "INVALID_INPUT", "detail": "이유"}`. 같은 내용을 다시 보내도 같은 결과이므로 재시도하지 않는 것을 권장한다 |
| 아직 받을 수 없음 (서버 종료 중, LLM 설정 누락) | `503` + `{"error": "NOT_READY", "detail": "이유"}`. 백엔드는 2xx가 아니면 보낼 것을 남겨 두고 10초 뒤 다시 보낸다 |

`batch` 번호는 1부터 빠짐없이 이어져야 받는다. 마지막으로 받은 번호가 6이면 7만 받고, 9가 오면 `409` + `{"expectedBatch": 7}`로 답한다.

요약 모델 호출은 길어질 수 있다. 측정값은 Gemini, 29분 회의 1건 기준 중앙값 약 5초, 최대 약 42초이다. 10초 주기를 맞추려면 요약이 끝나기를 기다리지 않고 바로 응답해야 한다.

## 8. 복구

ai-service는 회의 상태를 메모리에만 둔다. 재시작하면 상태가 없다.

| 순서 | 내용 |
|---|---|
| 1 | 재시작 직후 모르는 회의의 묶음이 오면 `409` + `{"expectedBatch": 1}`로 답한다 |
| 2 | 백엔드가 그 회의의 묶음을 1번부터 보냈던 그대로 다시 보낸다. 백엔드는 묶음을 회의가 끝나고 5분 뒤까지 보관한다 |
| 3 | 번호가 이어지는 동안 모두 받으면 복구가 끝난다. 번호 건너뜀 처리(7장)와 같은 방식이라 따로 만든 기능은 없다 |

- 회의 알림(`start` 등)은 다시 보내지 않아도 묶음만으로 복구된다. 다만 재시작 전의 `pause`·`resume` 상태는 복구되지 않는다.
- 재시작 뒤 만드는 회의 중 요약의 `version`은 시각(밀리초) 이상으로 시작하므로 재시작 전보다 작아지지 않는다 (`output-contract.md`).

## 9. 협의 상태

| 항목 | 상태 |
|---|---|
| 필드 이름과 타입 | AI 제안, 백엔드 답변 대기 |
| 받는 주소와 HTTP 방식 | 현재 주소는 임시, 백엔드 초안에 맞춰 바꿈 |
| 밀어 주기(백엔드 → AI) | AI 희망, 백엔드 답변 대기 |
| `end` 알림 전에 마지막 줄 묶음 | AI 요청 |
| `edits`에서 `speakerLabel` 제거 | AI 요청 |
| `edits`의 `rev` | 답변 받음 (2026-10-20): 1부터 시작하지 않고 줄마다 이어서 매긴다. 예: STT 확정이 `rev` 2였다면 사용자 수정은 3. 같은 `seq`는 `rev`가 큰 것만 반영한다 |
| `manual` 줄 | 답변 받음 (2026-10-20): 줄 직접 추가가 요구사항에 없어서 항상 `false`이고 오지 않는다. 요구사항이 정해지면 `startMs`·`endMs` 결정 방식을 다시 정한다 |
| 번호 건너뜀·재시작 복구 | 확정 (2026-10-20): `409` + `expectedBatch`, 백엔드는 묶음을 회의 종료 5분 뒤까지 보관 |
| 준비 안 됐을 때 | 구현 (2026-10-20): `503`, 백엔드는 10초 뒤 다시 보냄 |
| `textMarked` | 쓰지 않기로 함 (2026-10-16) |
